## Finding and rationale
Unique event IDs and idempotent upload prevent a repeated upload of the same ID from creating duplicate rows. They do not define a single logical answer attempt when a client accidentally assigns two IDs, a user reopens a stale object, an answer is corrected, or a retry occurs after an uncertain acknowledgment. The MVP gate “Every answer creates one durable event, including after retry” needs an explicit attempt identity and transaction boundary.

## Evidence (URLs, observed tests, or explicit unknowns)
Internal: section 6 defines event_id and object_version but no attempt_id or causal relation; section 8 merges append-only observations by ID; section 13 expects one event after retry. No client or store behavior has been tested.

## Proposed change and alternatives
Specify a stable attempt_id created when an answer interaction begins, with event_id for individual observations, plus rules for corrections, second attempts, stale content, and acknowledgment recovery. Commit accepted attempts and their deduplication keys atomically. Simpler first-slice alternative: permit only one submitted attempt per object presentation and record subsequent answers as distinct explicit attempts, not inferred retries.

## Implementation impact and acceptance test
Changes event schema and client queue contract before implementation. Simulate lost acknowledgment, duplicate upload with same ID, duplicate logical answer with a new event ID, legitimate second attempt, and stale object version; verify exactly the intended attempt count and recorded causal links after restart.
