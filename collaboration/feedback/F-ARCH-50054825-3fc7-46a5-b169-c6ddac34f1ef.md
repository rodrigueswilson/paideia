## Finding and rationale
The baseline says "no duplicate source-of-truth stores" and requires backup/restore. It does not classify Paideia's data by whether it can be recreated, or say which state is derived. Without that, three things go wrong:
- Backups grow with extraction artifacts and indexes.
- Restore tests become slow and therefore get skipped.
- Every change to the learner model or the ranking needs a data migration.

For one learner the irreplaceable data are small: events, approvals and edits of learning objects, annotations the learner makes in Paideia, ExternalReference mappings and settings. Extractions, FTS indexes, LearnerState and feed rankings can all be rebuilt from the originals and those records, provided they are computed deterministically.

## Evidence (URLs, observed tests, or explicit unknowns)
- Baseline: "Keep originals in their authoritative repositories; store normalized artifacts and metadata with hashes"; LearnerState has an "estimator version"; the event log is "append-only by default"; "Do not sync a live SQLite file through cloud drive"; MVP gate "Backup/restore ... tested".
- VERIFIED: SQLite's online backup API and VACUUM INTO both produce consistent snapshots. Copying the file during a transaction can corrupt the copy; copying while idle is safe only if the -wal/-journal file is copied too. Sources: https://www.sqlite.org/backup.html ; https://www.sqlite.org/lang_vacuum.html ; https://www.sqlite.org/howtocorrupt.html

## Proposed change and alternatives
Recommended:
- Add a one-page data authority table. For each entity, list its authority (Zotero, Obsidian, Anki or Paideia), what kind of copy Paideia holds (reference, derived cache or owned), and its refresh and deletion rule.
- Keep two stores on the host. `core.db` holds owned, irreplaceable data and stays small. `derived/` holds extractions, FTS indexes and caches, and can be deleted. LearnerState and rankings are projections that a versioned function recomputes from the events; they are stored only for speed.
- Back up with a scheduled VACUUM INTO of core.db plus a manifest of document hashes. Rotate the copies and move them off the host. Never sync the live file through a cloud drive. Run a restore drill as one of the regular automated checks.
- Correct an event by adding a new event that names the one it supersedes, so the log stays append-only. Deletion for privacy is an explicit, logged purge.

Alternative: a single database, with derived tables marked by a `derived_` prefix and a documented rebuild script. Slightly simpler, with larger backups.

## Implementation impact and acceptance test
Decide now: the owned-versus-derived classification, and that learner state is a projection that can be rebuilt. Defer: retention periods, the choice of encryption at rest, and the off-host backup target (an owner privacy decision, Q-13). Cost of getting it wrong: lost learning history, which cannot be recovered, or a migration on every estimator change.

Test with a fixture database of 20,000 synthetic events:

- Restore from backup into a clean directory. Pass: the same orderings.
- Record the backup size and the rebuild time.
