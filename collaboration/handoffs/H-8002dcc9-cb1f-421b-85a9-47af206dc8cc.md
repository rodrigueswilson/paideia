### Three architecture decisions needed before implementation
1. Scheduler authority rule (owner): every item has exactly one scheduler. Anki items are graded only in Anki or AnkiDroid; Paideia pushes notes one way and reads review logs. The mechanism can be decided later.
2. Identity and provenance keys: Source = UUID + ExternalReference; Document = byte hash; Extraction = (hash, engine, version, settings); anchors = TextQuoteSelector plus a position hint. A quotation that fails the exact-match check cannot be approved.
3. Data ownership and flow: an authority table per entity, owned versus derived stores, learner state as a rebuildable projection, and a mobile rule that the device writes only append-only events, never shared mutable state.
(Gate for the stack only, not for these decisions: the Research MCP reuse classification.)

### Proposed first vertical slice
Windows host, one backend process, one SQLite core database with FTS5, and one responsive web UI. The steps:
1. Read one test Zotero item (read-only) and its PDF, plus one synthetic Kindle-format Obsidian note.
2. Extract the text layer, anchor segments and check quotations.
3. Generate one verified quotation and one retrieval/comprehension question per passage, with a GenerationRecord and schema validation.
4. The owner approves.
5. A timed, topic-filtered feed session on desktop, and online over the LAN on the phone and tablet.
6. Each answer creates one idempotent event.
7. A documented rule changes the next ordering.
8. One-way push of approved cards to a disposable Anki profile and a review-log import.
9. A VACUUM INTO backup and a restore drill.

Explicit exclusions: offline/Android packaging and sync; editing on the device; German content and exercises; OCR and Docling; semantic/vector search; Neo4j and the graph UI; adaptive or ML recommenders; FSRS; audio; remote/internet access; any write to production Zotero, Obsidian, Kindle, Anki or Research MCP data.

### Strongest argument against this review
The thin-boundary slice (F-ARCH-08774c84...) and the up-front identity design front-load integration work before the owner has seen any learning value. If the Zotero, Kindle or Anki audits reveal awkward formats, the first usable feed could slip by weeks. A plain PDF-to-feed loop would show sooner whether generated questions are even worth studying, which is arguably the largest product risk. Also, if Research MCP turns out to be unsuitable, the gate in F-ARCH-3814c990... only adds delay. The counter-position deserves a fair hearing: build the PDF-only loop first with the identity and scheduler-domain fields in its schema, and run the boundary spikes in parallel.
